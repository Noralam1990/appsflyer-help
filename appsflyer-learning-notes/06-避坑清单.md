# AppsFlyer 避坑清单

## 归因和报表

- 不要把 AppsFlyer install 时间等同于 App Store / Google Play 下载时间。AppsFlyer 归因通常从首次打开开始记录。
- 不要期待 AppsFlyer、Meta、Google、TikTok、ASA、商店后台完全一致。先对齐 attribution model、窗口、timezone、数据延迟。
- 不要混用 LTV 和 Activity。Overview/Events/Cohort 常见是 LTV 思路，Activity 是行为发生日。
- 不要只看 last-touch。Assisted installs 能帮助理解多触点影响，但主归因仍是一个来源。
- 不要把 organic 简单理解为自然搜索。它只是 AppsFlyer 没找到有效 paid/owned attribution source。
- 不要直接把 SKAN 和传统归因相加。先看 SSOT 或定义去重规则。

## 链接和 OneLink

- 不要把 OneLink template 当成最终增长链接。template 是路由逻辑，custom link 才是用户点击链接。
- 不要随意修改 `pid`。集成 partner 的 media source 标识通常有严格规则。
- 不要只传 campaign name，不传 campaign/adset/ad ID。name 后期会变，ID 更适合分析。
- 不要忘记 `is_retargeting=true`，否则再营销活动可能被当成 UA。
- 不要在 deep link 里只配 AppsFlyer 参数，app 内路由也必须开发实现。
- 不要忽略桌面点击 fallback。邮件、QR、CTV、社媒经常有 desktop/web 场景。
- 不要忘记 OneLink template 改动可能有生效延迟。

## SDK 和事件

- 不要上线前才补事件字典。事件字典应该先于开发。
- 不要大小写混用事件名。Partner mapping、postback、dashboard 都可能受影响。
- 不要把收入值写成带货币符号或逗号的字符串。
- 不要既用 ROI360 purchase/ad revenue 集成，又把同一笔收入作为普通 `af_revenue` 重复上报。
- 不要在没有理解影响前，把 privacy-preserving methods 放到 SDK `start` 之前。
- 不要只测 Android 或只测 iOS。两端 deep link、CUID、事件参数必须一致。
- 不要忘记离线事件、初始化前缓存事件、S2S 重试和去重。

## SKAN / iOS

- 不要把 SKAN 当实时数据。postback 延迟是机制的一部分。
- 不要把 Window 2 当 D0-D7 累计。SKAN 4 的三个窗口是非重叠的。
- 不要盲目追求复杂 CV schema。复杂不等于可优化，低样本会带来 null/coarse。
- 不要只看 fine CV。coarse CV 和 null CV 的比例本身就是信号。
- 不要忘记 partner event postback mapping。Conversion Studio 配了事件，不代表 partner 一定收到。
- 不要关闭或调整 AAP / Advanced Privacy 而不走法律和数据治理确认。
- 不要忽略 Apple 官方文档。SKAN 规则底层由 Apple 决定。

## Partner Integrations 和 Postbacks

- 不要一键给 partner 开过多权限。尤其是 all media sources including organic。
- 不要以为所有 partner 都支持同样字段、postback、cost、SKAN、deep link。
- 不要忽略 SRN 的特殊性。SRN 不通过普通 attribution link 传点击，raw clicks/impressions 可能不可见。
- 不要给 partner 映射不存在或拼写不同的事件名。
- 不要把 rejected events 当普通 events 解读。Protect360 或 validation rules 可能已经拦截。
- 不要忘记 agency、ad network、team member 的权限会影响他们能看到的数据。

## ROI360

- 不要只看 CPI 优化。低 CPI 可能带来低留存、高 fraud、低 ROAS。
- 不要混淆 ad revenue、IAP、subscription、store revenue。
- 不要假设成本和收入都能历史回填。很多数据从集成当天开始。
- 不要忽略 timezone 和 currency。成本、收入、raw data、dashboard 可能显示规则不同。
- 不要在 BI 中重复合并同一来源的成本或收入。

## Data / BI

- 不要把 raw data API 拉满 200K / 1M 行还当作完整结果。达到上限就要切窗口补拉。
- 不要忘记 Data Locker availability window。
- 不要把 Push API 的字段选择设一次就永远不管。新字段可能不会自动进入。
- 不要把 AAP 下缺失的字段当作上报错误。
- 不要把 campaign name 当稳定主键。
- 不要忽略 `is_primary_attribution`，尤其是 retargeting 和 UA 同时存在时。

## Protect360

- 不要以为 Protect360 会阻止真实用户安装。通常用户仍可安装使用，只是归因/数据被拦截或标记。
- 不要只看 real-time blocked，也要看 post-attribution fraud。
- 不要用普通 dashboard 对账 fraud，Protect360 dashboard 和 raw data 是主入口。
- 不要随便建立过宽 validation rules，可能误杀真实流量。
- 不要把某个 publisher 一天异常当结论，要结合 CTIT、CVR、new devices、event quality、post-attribution。

## Audiences / Incrementality

- 不要把 audience 当静态名单。用户会进出分群，连接 partner 后还有同步延迟和匹配率。
- 不要上传未经治理的 email/phone 等 additional identifiers。需要 hash、权限和条款确认。
- 不要把 remarketing 转化率直接当增量。Incrementality 要看 control/test 或 geo 实验。
- 不要同时让 UA campaign 面向现有用户，SRN 文档明确提到 mistargeting 会浪费预算。
