# AppsFlyer 核心知识笔记

## 1. AppsFlyer 到底解决什么问题

AppsFlyer 的核心是把四类东西连起来：

1. 用户从哪里来：广告点击、曝光、SRN 自报告、OneLink、web 参数、跨平台触点。
2. 用户是否真的来了：install、first open、reinstall、re-attribution、re-engagement。
3. 用户来了以后做了什么：session、注册、购买、订阅、广告展示、关键业务事件。
4. 这批用户值不值：成本、收入、ROI、ROAS、留存、欺诈、增量。

新手最容易卡住的点是把 AppsFlyer 当成“一个广告后台”。它更像一个独立口径的营销测量层。你的 Meta、Google、TikTok、Apple Search Ads、商店后台、BI 后台，都会有自己的计数规则，所以差异是常态。

## 2. 归因模型怎么理解

AppsFlyer 归因的基本问题是：某个用户安装或重新打开 app，应该归功于哪个触点？

常见归因方法：

- Android install referrer：Google Play 等商店把安装前来源传给 AppsFlyer。
- Device ID matching：通过 GAID / IDFA 等设备标识做确定性匹配。
- Probabilistic modeling：没有设备 ID 时用概率方式建模，受平台和隐私规则限制。
- SKAN：Apple 的 iOS 聚合归因，不提供用户级归因。
- Apple Search Ads：Apple 自身渠道归因。
- Deep link：用于已安装用户的 re-engagement 等场景。
- SRN：如 Google Ads、Meta、TikTok、Snap 等自报告网络，通过 API 和设备 ID / 隐私框架与 AppsFlyer 交互。

关键规则：

- AppsFlyer 中 install 通常在首次打开 app 后记录。
- 如果多个触点有效，点击一般优先于曝光。
- 确定性方法通常优先于概率方法。
- 最终只会有一个主归因来源，但 assisted installs 可显示其他辅助触点。
- SRN 不像普通渠道那样靠 AppsFlyer attribution link 传点击，很多点击/曝光原始数据不会出现在 raw data 中。

## 3. Attribution Links 和 OneLink

Attribution link 是归因数据的入口之一。它告诉 AppsFlyer：用户和某个媒体源、campaign、广告组、广告、publisher 发生了互动。

OneLink 是更高级的链接体系，用于：

- 一个链接覆盖 iOS、Android、desktop、web、CTV 等多个目的地。
- 新用户去商店或落地页。
- 已安装用户打开 app。
- 带 deep link 参数进入具体页面。
- QR、email、SMS、social、referral、web-to-app 等 owned media 场景。

要分清：

- OneLink template：路由逻辑模板，不是用户最终点击链接。
- OneLink custom link：基于 template 生成的真实增长链接。
- Link 参数：决定归因粒度和 deep link 行为。
- App Links / Universal Links / URI scheme：决定已安装用户能否打开 app。

OneLink 典型协作方式：

1. Marketer/Product 定义用户旅程：新用户去哪、老用户去哪、桌面用户去哪。
2. Developer 配置 Android App Links、iOS Universal Links、SDK deep link listener。
3. Marketer 创建 template 和 custom links。
4. UA/Data 通过 Overview、Events、Cohort 或 raw data 验证归因和行为。

## 4. SDK、事件和 CUID

SDK 是移动端数据进入 AppsFlyer 的基础。开发侧最重要的不是“装上 SDK”，而是保证以下内容稳定：

- 初始化时机正确。
- 首次打开能被记录。
- in-app events 能按统一命名和参数结构发送。
- revenue、currency、content ID、subscription、ad revenue 等字段不乱。
- CUID 在用户登录或业务识别后设置，用于跨设备、CRM、audience、BI join。
- 隐私方法调用时机清楚：在 `start` 前后调用会影响 attribution 或后续数据可用性。
- Android / iOS SDK release notes 在上线前确认最新版本。

事件设计原则：

- 先定义业务漏斗，再定义 AppsFlyer event。
- 事件名要稳定、大小写统一、跨平台一致。
- revenue 只在需要计入收入的事件里传。
- 如果使用 ROI360 的 purchase connector 或 ad revenue SDK API，不要重复用普通 in-app event revenue 上报同一笔收入。
- S2S 事件要带足必要 ID，否则可能无法归因、无法进 Incrementality、无法用于 SKAN 或 partner postback。

## 5. Dashboards：先问问题，再选报表

不要一上来就问“哪个报表最准”。先问你要回答什么：

| 问题 | 优先看 |
|---|---|
| 某个渠道带来的用户总体质量怎么样 | Overview |
| 今天 app 活跃、session、收入怎么样 | Activity |
| 注册/购买/订阅事件由哪些渠道贡献 | Events |
| D1/D7/D30 留存和收入回收怎么样 | Cohort |
| iOS SKAN campaign 表现怎么样 | SKAN Dashboard |
| 我要跟 BI、渠道、后端逐条对账 | Raw data / Data Locker / Pull API |
| 我要看 fraud 被拦了多少 | Protect360 Dashboard / raw data |

关键口径：

- LTV 报表按归因/安装时间看后续累计价值。
- Activity 报表按事件发生时间看当天实际行为。
- Cohort 报表按一批用户的生命周期看趋势。
- SKAN 报表来自 Apple postback，延迟和粒度限制是设计的一部分。

## 6. ROI360：为什么只看安装不够

UA 优化不能只看 install、CPI、注册数。真正的问题是：

- 花了多少钱？
- 带来了多少 IAP、订阅、广告收入？
- 这些收入归属于哪个媒体源、campaign、ad set、ad？
- 数据延迟和重复上报是否可控？

ROI360 把成本和收入补齐：

- Cost：API、CSV cost import、link cost 参数等。
- Revenue：IAP、订阅、store revenue、ad revenue。
- Ad revenue：可通过 API 或 SDK impression-level 方式接入，SDK 粒度通常更新更快，也支持 SKAN 场景。
- Cost ETL：把更细粒度成本送进 Data Locker，给 BI 使用。

避坑：

- 成本和收入的 timezone、currency、更新时间要明确。
- ad revenue 和 in-app event revenue 不要重复计算。
- 历史数据不一定能回填，很多收入/成本从集成当天开始。

## 7. Partner Integrations 和 Postbacks

Partner Integrations 是渠道管理中心。典型任务：

- 从 Marketplace 找 partner。
- 激活某个 app 的 partner。
- 配置 attribution windows、cost、ad revenue、SKAN、deep link、permissions。
- 配置 default postbacks 和 in-app event postbacks。
- 决定 postback 是发给 attributed partner，还是 all media sources including organic。

Postback 是 AppsFlyer 把 install、event、revenue、rejected event 等信息发给 partner 的机制。它会影响渠道优化，也会影响隐私和合规风险。

关键避坑：

- 事件名大小写敏感。
- Partner 事件映射要和 SDK / S2S 事件完全一致。
- “All media sources including organic” 会把更大范围数据发给 partner，必须谨慎。
- SRN 有自己的归因和深链逻辑，不要假设普通 attribution link 的所有字段都存在。

## 8. Protect360、ProtectLITE 和 Validation Rules

ProtectLITE 是基础 fraud 检测，Protect360 是高级反作弊产品。

Protect360 处理两类时间点：

- Real-time blocking：归因前识别并拦截，blocked installs/events 不进入普通归因报表。
- Post-attribution detection：先归因，之后识别为 fraud，需要在对账和优化中处理。

常见 fraud：

- Click flooding
- Install hijacking
- Click hijacking
- Device ID reset fraud
- Bots / emulators / device farms
- Behavioral anomalies
- SDK spoofing

Validation Rules 是你自定义的一层规则，可用于：

- 拦截不符合 IO 的 geo / OS / campaign。
- 拦截异常收入或事件。
- 防止错误定向或被劫持的安装。

## 9. Audiences 和 Incrementality

Audiences 用于把用户按条件圈出来并同步给渠道：

- 活跃但未购买用户。
- 高价值付费用户。
- 需要排除的现有用户。
- 注册未转化用户。
- 从内部 CRM / BI 导入的用户。
- 基于 CUID 或 device ID 的用户群。

Incrementality 解决另一个问题：这次广告是否真的带来了额外转化？

- Attribution 告诉你“谁最后拿到了归因”。
- Incrementality 告诉你“如果不投广告，这些转化是否还会发生”。
- UA Incrementality 更偏 geo-experiment。
- Remarketing Incrementality 更偏 test/control group。

## 10. Web 和 Cross-platform

AppsFlyer 已经不只是移动 app。公开文档中还有：

- Web Attribution：识别网站访问和 web event 的媒体来源。
- Web SDK / Web S2S：前端或服务端采集 web visit/event。
- Product line：把 web 和 app 放进跨平台 LTV 视角。
- CTV、PC、Console：支持 cross-platform attribution flows 和 Data Locker 报告。
- Smart Script：用于 web-to-app 或 cross-platform landing page 场景。

注意：很多 Web Attribution 页面仍标注 Beta，实施前要确认账户可用性和产品状态。
